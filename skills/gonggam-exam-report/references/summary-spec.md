# 요약본 규격 (정본)

`assets/template_summary.html` 이 지키는 규격이다. **A4 딱 한 장.**
본편 리포트 규격은 `report-schema.md` 가 갖고, 이 문서는 «한 장으로 줄일 때 무엇을 남기고
무엇을 버리는가» 만 정한다.

> 학부모 카톡·문자에 첨부하고, 상담 탁자 위에 올려놓는 종이다.
> **40초 안에 읽힌다**는 전제로 만든다. 못 읽히면 분석이 아무리 정확해도 소용이 없다.

---

## 0. 한 장 원칙

| | |
|---|---|
| 판형 | A4 210×297mm · `@page{size:A4;margin:16mm 14mm}` |
| 본문 폭 | 182mm |
| 본문 높이 | **265mm 고정** (`.sheet{height:265mm}`) |
| 쪽수 | **1쪽.** 2쪽이 되면 발행 불가 |
| 모션 | 없다. 인쇄물이다 |
| 색 | `{{THEME_CSS}}` 가 넣는 변수만 (`--primary` `--accent` `--ink` `--muted` `--line` `--gray-pale` `--primary-pale` `--paper`) |
| 글꼴 | `{{FONT_CSS}}` 가 넣는 `'ReportKR'` 하나 · 굵기 **400 / 700 / 900** 셋 |

**색·글꼴을 값으로 적지 않는다.** 테마(`clean` `gonggam` `mono` `warm`)를 갈아 끼워도
같은 조판이 나와야 한다. 흑백 복사를 거칠 예정이면 `mono` 로 뽑는다.

### 굵기는 셋뿐이다 — 400 · 700 · 900

| 굵기 | 쓰는 곳 |
|---|---|
| **900** | 학교명 · 과목 · 숫자 카드 값 · 난이도 숫자 · 대표 문항 번호/제목 · 한 줄 결론 |
| **700** | 라벨 · 배지 · 칩 · 캡션 · 강조 어구 |
| **400** | 본문 전부 (발췌 · 이유 · 조건 · 마무리 본문) |

**600·800 같은 중간값을 쓰지 않는다.** 동봉 폰트에 없는 굵기는 브라우저가 가장 가까운 쪽으로
말없이 옮긴다 — 800 은 900 으로 올라붙어 **온 종이가 굵어지고 대비가 사라진다.**
(실제로 800 을 스무 군데 쓰고 있었다. 900 이 들어오면서 전부 굵어질 자리였다.)

제목에는 자간 **`-.02em`** 을 준다. 900 은 글자가 굵어 그만큼 서로 붙여야 덩어리로 읽힌다.
**굵기를 바꿔도 조판 높이는 그대로다** — 400·700·900 셋을 다 넣고 다시 재서 확인했다.
지금 판형의 기준값은 머리글 17.2 · 카드 16.7 · 밴드 52.6 · 대표 문항 86.4mm 다 (§3).

## 1. 만드는 법

```bash
python scripts/render_report.py report.json out/ --summary              # 배포본
python scripts/render_report.py report.json out/ --summary --internal   # 내부 확인본
```

`--summary` 는 `assets/template_summary.html` 을 쓴다. 그 파일이 없으면 렌더가 **실패한다** —
본편 템플릿으로 슬쩍 대체하지 않는다.
렌더러가 PDF 까지 만들고 **PDF 를 열어 쪽수를 실측**한다. 꼬리말의 쪽 표시는 그 실측값이다.

표본은 `examples/summary.sample.json`. 규격을 고치면 표본도 같이 고치고 렌더를 다시 돌린다.
둘이 갈라지면 규격이 죽는다.

## 2. 데이터 계약

**요약본 입력은 본편 `report.json` 과 같은 파일이다.** 아래 셋만 다르다.

1. `sections` 를 요약본이 아는 여섯 개로 줄인다
   (`overview` `type-chart` `radar` `difficulty` `killer` `summary`)
2. `killer` 를 **한 개**로, `types` 를 **상위 세 개**로 잘라서 넘긴다
3. `issues` 와 `next_action` 을 더한다

`items` 는 그대로 둔다. 요약본 템플릿이 직접 읽지는 않지만
**난이도 5칸을 렌더러가 `items` 에서 세고**, 게이트의 데이터 검사가 그것을 본다.

`chapters` 도 그대로 둔다. `chapter-ratio` 섹션은 요약본에 없지만 **「많이 나온 유형」
상자의 발이 `chapters[0]` 을 읽는다**(§2-1). 빼면 `chapters.0.name` 이 안 채워져
**렌더가 실패한다.** 섹션이 없으니 데이터도 필요 없겠거니 하고 빼지 않는다.

### 2-1. 요약본이 싣는 섹션

| 섹션 키 | 요약본에서 | 쓰는 데이터 |
|---|---|---|
| `overview` | 숫자 카드 4 | `overview.cards[{label,value,num,unit,key}]` — **정확히 4개** |
| `difficulty` | 난이도 5단 카드 | `difficulty.bins[{label,count}]`(자동) · `difficulty.summary` · `meta.total_items` · 발에 `killer[0].no` `killer[0].kind` |
| `radar` | 유형별 배점 레이다 | `radar{ok,points,rings[],spokes[],axes[]}`(자동) — **전 유형**으로 그린다 |
| `type-chart` | 많이 나온 유형 | `types[{name,count,points,em,width}]` — **상위 3개만** · `overview.highlight` · `meta.total_points` · 발에 `chapters[0].name` `chapters[0].points` |
| `killer` | 대표 문항 | `killer[{no,title,kind,why,excerpt,choices[],conditions[],answer,concepts[]}]` — **1개만** |
| `summary` | 한 줄 결론 + 근거 + 다음 행동 | `summary{quote,desc}` · `difficulty.discriminator` · `next_action` |

**카드의 `num`·`unit`·`key` 는 사람이 적지 않는다.** `report_build.py` 의 `split_cards` 가
`value`(「25문항」)를 숫자와 단위로 가른다. 단위가 빈 칸(=숫자로 시작하지 않는 «말» 카드)이
강조 칸이고, **넷 중 하나뿐**이다 (`layout-grammar.md` §3 · §0-2).

**막대의 `em` 도 사람이 적지 않는다** — `exam.json` 의 `emphasis` 가 지목한 줄에만 붙고,
지목이 없으면 모든 줄에 빈 값이 붙는다. **빈 값이라도 모든 줄에 있어야 한다.**
렌더러에 「만약」이 없어서 한 줄이라도 빠지면 `{{em}}` 이 남아 렌더가 멈춘다.
`width` 는 렌더러의 `derive` 가 배점에서 낸다.

**레이다는 상위 3개가 아니라 전 유형으로 그린다.** 막대(상위 3)와 같은 데이터를 다른
범위로 보는 것이라 둘이 어긋나 보일 수 있는데, 그것이 의도다 — 막대는 「무엇이 컸나」,
레이다는 「배점이 고르게 퍼졌나」를 말한다. 상자 머리의 「전 유형」이 그 범위를 밝힌다.
**축이 셋 미만이면 `radar.ok` 가 비고 상자가 통째로 사라진다** — 둘로는 다각형이 안 선다.
그때 밴드는 52.6mm 에서 48.6mm 로 줄고, 그만큼 꼬리말 위 여백이 늘어난다 (§3).

**이슈 문항은 `sections` 가 아니라 «데이터» 가 켜고 끈다.** 그 상자만은 SECTION 으로 감싸지
않았다 — `issues` 가 빈 목록이면 저절로 사라진다. 그래서 `sections` 에 `issues` 를 적어도
되고(빈 자리를 따로 두었다) 안 적어도 된다. `report_build.py` 의 `SUMMARY_SECTIONS` 처럼
`issues` 가 없는 목록을 그대로 넘겨도 이슈 상자는 제대로 찍힌다.

섹션 밖(항상 찍히는 것): 로고(`brand.academy` · `brand.logo_path`) · `meta.school`
`meta.grade_label` `meta.term` `meta.scope` `meta.subject` `meta.total_items`
`meta.total_points` · `disclaimer`.

### 2-2. 요약본이 «싣지 않는» 섹션

`items` · `chapter-ratio` · `grade-cut` · `study-plan` · `parent-note` 는
**한 장에 들어가지 않는다.** 본편 리포트에만 있다.

템플릿 맨 아래에 이 다섯 개의 **빈 자리**가 있다(`issues` 자리까지 여섯). 본편 `sections`
목록을 그대로 넘겨도 렌더가 죽지 않게 하려는 것이고, 넘겨도 **아무것도 찍히지 않는다.**
요약본을 만드는 쪽은 §2-1 표의 여섯 개를 적는 것을 원칙으로 한다 —
`issues` 는 그 위에 더해도 되고 안 더해도 된다(표본은 더해 둔다).

**섹션을 안 싣는 것과 데이터를 안 넘기는 것은 다른 이야기다.** `chapter-ratio` 섹션은
안 싣지만 `chapters` 데이터는 넘긴다(§2). `study-plan` · `parent-note` 도 섹션으로는
안 싣지만, 그 데이터가 있어야 채움 블록을 켤 수 있다 (§4-1).

### 2-3. 요약본 전용 필드

| 필드 | 필수 | 뜻 |
|---|---|---|
| `killer[0].kind` | ✔ | **`객관식` 또는 `서술형`.** 대표 문항의 꼴을 가른다 (§2-4). 머리줄 오른쪽 배지와 난이도 상자 발(「그 갈래」)에도 이 값이 그대로 찍힌다 |
| `killer[0].excerpt` | ✔ | 대표 문항 지문·발문 발췌. **줄바꿈이 그대로 살아난다** (`white-space:pre-line`) |
| `killer[0].choices[]` | ✔ | 선지 문자열 목록. 번호(①②…)는 **적지 않는다** — 템플릿이 1부터 매긴다. **서술형이면 `[]`** |
| `killer[0].conditions[]` | ✔ | 〈조건〉 상자에 들어갈 줄. **객관식이면 `[]`** |
| `killer[0].answer` | ✔ | 객관식이면 **정답 숫자**, 서술형이면 **모범답안 한 줄** |
| `issues` | ✔ | 없으면 **빈 목록** `[]`. 키를 아예 빼면 렌더가 실패한다 |
| `issues[0].kind` | | `복수정답` `조건누락` `범위밖` `배점과다` `유형급변` 다섯 중 하나 |
| `next_action` | ✔ | **학원이 할 일 한 줄.** 학부모가 할 일이 아니라 학원이 할 일을 적는다 |
| `study_plan[]` | | 채움 블록 1순위가 쓴다 (§4-1). 없으면 그 블록을 못 켠다 |
| `parent_note[]` | | 채움 블록 2순위 |
| `difficulty.detail[]` | | 채움 블록 3순위 · `{label,count,points,nos}` |

`killer[0].no` 는 대표 문항 머리줄·발췌 캡션만이 아니라 **난이도 상자 발**(「가장 갈린 문항」)에도 쓰인다. 두 자리가 같은 값을 읽으므로 따로 적는 칸이 없다.

**선지에 정답을 칠하지 않는다.** 렌더러에 조건문이 없기도 하지만,
무엇보다 **흑백 복사에서 칠은 사라진다.** 정답은 선지 아래 칸에 숫자로만 적는다.

`killer` 에 둘 이상을 넣으면 **대표 문항 상자가 그만큼 반복되어 2쪽이 된다.**
자르는 것은 요약본을 만드는 쪽(`killer[:1]`)이다. 템플릿은 자르지 않는다 —
조용히 버리면 「왜 15번이 안 나왔지」를 아무도 모른다. `issues` 도 같다.

### 2-4. 대표 문항은 두 꼴이다 — 객관식 · 서술형

킬러문항은 기계가 고른다 (난이도 `상` 중 배점 높은 순). 그래서 **배점 높은 서술형이
1순위가 되는 일이 흔하다.** 규칙을 깨서 객관식을 고르게 하지 않는다 — 실제로 가장 많이
갈린 문항이 그것이기 때문이다. **템플릿이 두 꼴을 받는다.**

| | 객관식 | 서술형 |
|---|---|---|
| 발췌 | 지문 | 지문 + 발문 |
| 그 아래 | **선지** ①~⑤ | **〈조건〉 상자** |
| 답 칸 이름표 | 「정답」 | 「모범답안」 |
| `answer` 값 | `"2"` | `"(A) routine   (B) belonging"` |
| 빈 목록 | `conditions: []` | `choices: []` |

**「본문참조」를 학부모가 받는 종이에 찍지 않는다.** `items[].answer` 의 «본문참조» 는
내부 표기다. 서술형 대표 문항의 `killer[0].answer` 에는 **모범답안 한 줄**을 적는다.

**가르는 장치는 빈 목록이다.** 렌더러에 «만약» 이 없으므로, 선지 상자와 조건 상자는
각각 `REPEAT` 가 0번 돌면 **진짜로 빈 칸**이 되고 `:empty` 가 자리째 없앤다.
`kind` 는 답 칸 이름표(「정답」/「모범답안」)와 머리줄 배지에만 쓴다.
그래서 **`choices` 와 `conditions` 는 둘 다 «있어야» 한다** — 안 쓰는 쪽을 `[]` 로.
키를 아예 빼면 `REPEAT 대상이 report.json 에 없습니다` 로 렌더가 멈춘다(조용히 비지 않는다).

## 3. 지면 배분

위에서 아래로 이 순서다. 블록 사이 간격 3.2mm.
실측은 표본 둘(`summary.sample.json` = 객관식, `summary.seosulhyeong.sample.json` = 서술형)을
크롬으로 재서 얻은 값이다. **발췌를 둘 다 5줄로 맞추고** 이슈 1개 · 레이다 있음 ·
고지 3줄로 잰 것이다 (표본 그대로면 서술형 발췌가 4줄이라 대표 문항이 4.7mm 작다).

| 블록 | 설계 | 표본 실측 | 내용 |
|---|---|---|---|
| 머리글 | 20mm | **17.2mm** | 학원 로고 · 학교/학년 · 시험명/범위 · 과목 |
| 숫자 카드 4 | 22mm | **16.7mm** | 값·단위 한 덩어리 + 아래 라벨. 넷 중 하나만 강조 |
| 밴드 — 난이도 5단 · 레이다 · 유형 상위 3 | 50mm | **52.6mm** | 2×2 카드 셋. 레이다가 빠지면 **48.6mm** |
| **대표 문항 · 객관식** | 50mm | **82.2mm** | 머리줄 + 발췌 5줄(26.8) + 캡션 + 선지 5(14.9) + 정답 칸(6.4) + 이유·칩 |
| **대표 문항 · 서술형** | 50mm | **86.4mm** | 머리줄 + 발췌 5줄(26.8) + 캡션 + 〈조건〉 3줄(23.1) + 모범답안 칸(6.4) + 이유·칩 |
| **이슈 문항** | 35mm | **23.5mm** | 있을 때만. 갈래 배지 + 이유 2줄 + 조건 발췌 |
| 마무리 **칸**(`.closing`) | — | 남는 만큼 | 아래 상자 + 그 밑 흰 여백 |
| └ 마무리 **상자**(`.final`) | 30mm | **32.6mm** | 좌우 2열. 왼쪽 한 줄 결론 / 오른쪽 근거 + 다음 행동. **내용 높이 고정** |
| 꼬리말 · 고지 | 10mm | **13.6mm** | 출처 표기 · 추정치 고지 · 쪽 표시. **고지 한 줄에 3.8mm** |
| 합 | 217mm | **265.0mm** | 두 꼴 모두 넘침 0.0mm · 1쪽 |

**합이 딱 떨어진다.** 블록 높이를 다 더하고 사이 간격을 더하면 265.0mm 다 —
간격은 «블록 수 − 1» 개다. 이슈가 있으면 블록 일곱(간격 19.2mm), 없으면 여섯(16.0mm).
서술형·이슈 있음으로 세어 보면
`17.2+16.7+52.6+86.4+23.5+35.8+13.6 = 245.8`, 간격 `6×3.2 = 19.2`, 합 **265.0** 이다.
이 셈이 §4-1 의 «남는 자리» 를 계산으로도 낼 수 있게 해 준다.

**꼬리말은 판형이 아니라 `disclaimer` 가 키운다.** 표본의 고지가 78자에서 135자로 길어지면서
꼬리말이 9.7 → **13.6mm** 가 됐다 — 한 줄에 3.8mm 다. 그 3.8mm 는 발췌 한 줄(4.7mm)에
맞먹어서, 고지를 한 줄 늘리면 **발췌를 한 줄 줄여야 하는 수가 있다** (§5).

**「왜 갈렸나」와 「총평」이 더는 두 블록이 아니다.** 예전에는 위아래 두 덩어리(17.6 + 26.7mm)
였는데, `layout-grammar.md` §9-1 의 비대칭 2열을 받아 **한 상자 32.6mm** 로 합쳤다.
왼쪽 150px 고정 칸에 한 줄 결론, 오른쪽 나머지에 근거와 다음 행동이다.
둘을 좌우로 붙이니 한 덩어리로 읽히면서 세로도 11.7mm 줄었다.

**「왜 갈렸나」의 옛 자리에 있던 `overview.highlight` 는 막대 아래로 내려갔다.**
지금은 「많이 나온 유형」 상자의 해석 문장이다 (`layout-grammar.md` §6).

**설계값은 «최소 확보량»이지 고정 높이가 아니다.** 실제 높이는 내용이 정한다.

- 머리글·카드·밴드·대표 문항·이슈·채움·꼬리말 = `flex:0 0 auto` (내용이 높이를 정한다)
- 마무리 **칸**(`.closing`) = `flex:1 0 auto`
  (**남는 자리를 받되 줄어들지는 않는다** — 아래 «조용한 사고» 참조)
- 그 안의 마무리 **상자**(`.final`) = `flex:0 0 auto` — **내용 높이 그대로.**
  남는 자리는 상자 **밖**, 꼬리말 위 흰 여백이 된다 (§4)

**상자를 늘려 자리를 채우지 않는다.** 예전에는 남는 자리를 상자가 먹되 52mm 에서
멈추게 했는데, 그러면 «내용보다 훨씬 큰 빈 파란 상자» 가 남았다 — 흰 종이가 아니라
**빈 강조**다. 파란 바탕이 넓으면 그 자체가 강조인데 정작 강조할 글은 위쪽에만 있다.
「강조가 많으면 강조가 없다」에 걸린다 (수동 검수에서 잡혔다).

남는 자리는 **여유분**이고, 발췌가 6줄로 늘거나 문장이 길어지면 거기서 먼저 깎인다.

### 조용한 사고 — 마무리 칸이 «줄어들면» 겹쳐 찍힌다

`.closing` 을 줄어들 수 있게 두면(`flex:1 1 auto` + `min-height`) 발췌가 길어질 때
그 칸이 **내용보다 작아지고**, 마무리 상자가 **꼬리말 위에 겹쳐 찍힌다.**
그런데 쪽수는 그대로 1쪽이라 **게이트도 통과한다** — 겹친 종이가 학부모에게 나간다.
실제로 발췌 8줄에서 그렇게 찍혔다(실측).

그래서 `flex:1 **0** auto` 다. 줄어들지 않으면 넘칠 때 **2쪽**이 되고,
「요약본 1쪽」이 막는다. **조용히 겹치느니 시끄럽게 막히는 편이 낫다.**

## 4. 이슈 문항이 없을 때

`issues` 가 빈 목록이면 그 상자는 **통째로 사라진다** (REPEAT 가 0번 돌기 때문이다).
빈 테두리도, 「해당 없음」도 찍지 않는다. 표본으로 잰 차이는 이렇다
(발췌 5줄 · 레이다 있음 · 고지 3줄).

| 블록 | 서술형 · 이슈 있음 | 서술형 · 없음 | 객관식 · 있음 | 객관식 · 없음 |
|---|---|---|---|---|
| 이슈 문항 | 23.5mm | **0 (사라짐)** | 23.5mm | **0 (사라짐)** |
| 마무리 칸(`.closing`) | 35.8mm | 62.4mm | 40.0mm | 66.7mm |
| └ 마무리 상자(`.final`) | **32.6mm** | **32.6mm** | **32.6mm** | **32.6mm** |
| 꼬리말 위 흰 여백 | 6.4mm | **33.1mm** | 10.6mm | **37.3mm** |
| PDF | 1쪽 | 1쪽 | 1쪽 | 1쪽 |

**늘어나는 폭은 26.7mm 다** — 이슈 상자 23.5mm 에 그 위 간격 3.2mm 이 함께 빠지기 때문이다.
네 칸 모두 정확히 그만큼 늘었다.

**마무리 상자는 네 경우에 같은 높이다.** 이슈가 빠져서 생긴 27mm 는 상자가 먹지 않고
**꼬리말 위 흰 여백**으로 남는다. 상자는 대표 문항(또는 이슈 문항) 바로 아래에 붙어 있다 —
결론과 근거는 한 덩어리인 마무리라서 떼어 놓지 않는다.

상자를 바닥에 붙이고 여백을 그 위에 두는 꼴도 뽑아 봤는데(`margin-top:auto`),
대표 문항과 마무리 사이가 벌어져 **마무리가 따로 노는 것으로** 읽혔다. 그래서 쓰지 않는다.

**레이다가 빠지면 여백이 4.1mm 더 난다.** 축이 셋 미만이라 `radar.ok` 가 비면 밴드가
52.6 → 48.6mm 로 줄기 때문이다 (§2-1). 위 표는 레이다가 **있는** 쪽이고, 그쪽이 더 빠듯하다.
채움 블록을 고를 때는 빠듯한 쪽을 기준으로 삼는다.

**발췌가 한 줄 짧으면 여백이 4.7mm 더 난다.** 서술형 표본은 발췌가 4줄이라 위 표(5줄)보다
그만큼 헐겁다 — 이슈 있음 11.1mm · 없음 **37.8mm**. §4-1 은 이 «표본 그대로» 값을 쓴다.

## 4-1. 채움 블록 — 빈 자리를 쓸모로 채운다

38mm 가 비면 학부모 눈에는 **«덜 만든 종이»** 로 보인다. 그래서 자리가 남으면
**쓸모 있는 것**을 넣는다 — 빈 상자로 부풀리는 것과는 다른 이야기다.
억지로 채우는 글은 여전히 금지다. 넣는 것은 **이미 분석해 둔 내용**뿐이다.

| 순위 | 섹션 키 | 블록 | 쓰는 데이터 |
|---|---|---|---|
| 1 | `fill-plan` | **다음 시험까지** — 주차 · 집중할 것 · 할 일 | `study_plan[{week,focus,todo}]` |
| 2 | `fill-home` | 가정에서 도와주실 것 | `parent_note[]` |
| 3 | `fill-difficulty` | 난이도별 문항 — 어디서 갈렸나 | `difficulty.detail[{label,count,points,nos}]` |

`difficulty.detail` 은 요약본 전용이다. `nos` 는 문항 번호를 «6·11·15» 처럼 가운뎃점으로 잇는다.

**판형은 최상위 데이터를 그대로 돈다.** 세 블록의 REPEAT 대상은 `study_plan` ·
`parent_note` · `difficulty.detail` 이지 `fill_blocks[].rows` 가 아니다.
그래서 빌더가 «앞의 2주만» 담아 넘겨도 **종이에는 `study_plan` 이 통째로 나간다.**
줄 수를 셀 때는 빌더가 자른 수가 아니라 **최상위 목록의 길이**를 본다.

### 실측 높이 (이 표가 정본이다 — 렌더러는 이 값으로 고른다)

서술형 표본 **그대로**(발췌 4줄), 이슈 없음, 레이다 있음, 고지 3줄에서 잰 값이다.
그때 꼬리말 위 흰 여백이 **37.8mm** 다 (렌더러가 PDF 에서 재는 잉크 띠는 그보다 0.3mm 크다).

> 2026-09-23 다시 쟀다 — 판형이 «지면 문법»(layout-grammar.md §2 §3 §6 §7 §9 §10)을 받아
> 밴드에 레이다가 서고 카드·대표 문항이 커지고 마무리가 좌우 2열로 합쳐졌다.
> **블록 네 꼴의 높이도 함께 바뀌었다** — 이전 표(19.5 · 29.4 · 23.7 · 33.1mm)는 옛 판형 값이다.

**같은 블록이 두 줄이면 렌더러는 «마지막 줄» 의 높이를 읽는다.** 그래서 블록마다
**큰 쪽을 아래에 둔다** — 작은 쪽을 읽고 켰다가 실제 줄이 더 많으면 한 장을 넘긴다.
줄 수는 빌더가 `fill_blocks[].rows` 에 담은 수가 아니라 **최상위 목록의 길이**다(위 참조).

| 블록 | 줄 수 | 높이 | 그때 남는 여백 | 결과 |
|---|---|---|---|---|
| `fill-plan` | 2행 | 19.9mm | 15.7mm | 1쪽 |
| `fill-plan` | 3행 | 24.9mm | 10.7mm | 1쪽 |
| `fill-plan` | 4행 | **29.8mm** | 4.8mm | **1쪽** (표본의 `study_plan` 이 4행이다) |
| `fill-home` | 2줄 | 19.1mm | 15.5mm | 1쪽 |
| `fill-home` | 3줄 | 24.1mm | 10.5mm | 1쪽 |
| `fill-home` | 4줄 | **29.2mm** | 5.4mm | **1쪽** |
| `fill-difficulty` | 3줄 | 24.1mm | 10.5mm | 1쪽 |
| `fill-difficulty` | 4줄 | 28.8mm | 5.8mm | 1쪽 |
| `fill-difficulty` | 5줄 | **33.5mm** | — | **2쪽** — 넘침 1.9mm |

**줄 수로 계산하려면** — 세 블록이 같은 틀이라 한 식으로 떨어진다.

```
fill-plan        높이(mm) = 10.0 + 4.95 × 행 수     (행마다 점선이 한 줄 든다)
fill-home        높이(mm) =  9.0 + 5.05 × 줄 수
fill-difficulty  높이(mm) = 10.0 + 4.70 × 줄 수
```

### 들어가는지 재는 식 — 빈 띠에서 **6.4mm** 를 뺀 것이 진짜 자리다 ★

블록을 켜면 그 높이만 드는 것이 아니다. 블록이 하나 늘면 **사이 간격이 하나 더 생기고**,
꼬리말 앞 간격 3.2mm 은 애초에 쓸 수 없는 자리다. 그래서 —

```
들어갈 수 있는 높이 = 꼬리말 위 흰 여백 − 3.2(꼬리말 앞 간격) − 3.2(블록이 더하는 간격)
```

표본(서술형·이슈 없음·발췌 4줄)이면 `37.8 − 6.4 = 31.4mm` 다.
그래서 `fill-difficulty` 5줄(33.5mm)은 **못 들어간다** — 억지로 켜면 1.9mm 가 넘쳐
두 장이 된다(실측). `fill-plan` 4행(29.8mm)은 들어간다.
발췌가 한 줄만 길어져도 그 자리가 발췌 한 줄만큼 줄어, 표본에서 들어가던 4행짜리
`fill-plan` 도 아슬아슬해진다.

- 두 블록을 한꺼번에 켜려면 «높이 합 + 3.2(둘 사이 간격)» 가 그 자리 안에 들어와야 한다.
  가장 작은 둘만 해도 42.2mm 라 31.4mm 자리에 안 들어간다. **한 번에 하나**라고 보면 된다
- 블록이 하나도 안 켜져도 조판은 그대로다. 이슈 문항이 있는 경우(여백 11.1mm)가 그렇고,
  그때도 1쪽이다 (실측)

**렌더러의 셈은 이보다 헐겁다 — 알고 쓴다.** `pick_fill` 은 위 표의 높이를 잉크 빈 띠와
**그대로** 견준다(6.4mm 를 빼지 않는다). 그래서 자리보다 큰 블록을 한 번 고를 수 있는데,
그리고 나서 «한 장을 넘겼다» 를 보고 **마지막 블록을 빼고 다시 그린다.**
한 장은 안 깨지고 렌더 한 바퀴를 더 돌 뿐이다. 고칠 자리는 렌더러의 비교식이지
이 표의 숫자가 아니다 — **표에는 잰 높이를 그대로 적는다.**

**남는 자리를 재는 쪽은 렌더러다.** 템플릿은 켜고 끌 자리(`<!-- SECTION:fill-… -->`)와
위 실측값만 제공한다. 짐작으로 고르지 않는다.

### 이 절을 고칠 때 — 렌더러가 이 글을 **글자로** 읽는다 ★

`spec_heights()` 는 이 문서의 줄을 훑어 «블록 이름 하나 + 숫자mm» 이 같은 줄에 있으면
그것을 높이로 읽는다. 표 안인지 본문인지 가리지 않는다. 그래서 —

- 설명 문장에 블록 이름과 mm 값을 **같은 줄에** 적지 않는다. 「발췌가 한 줄 길어지면
  첫째 블록이 4.7mm 어쩌고」 처럼 이름과 숫자가 한 줄에 놓이면, 그 문장 하나가 그 블록의
  높이를 **그 숫자로 바꿔 버린다.** 이 문서를 고치다 실제로 그렇게 됐다 —
  네 줄짜리 계획표가 5mm 도 안 되는 것으로 읽혀 늘 켜지는 상태가 됐다.
  이름을 써야 하면 숫자를 **다음 줄로** 넘긴다
- 두 블록을 한 줄에 같이 적으면 그 줄은 읽히지 않는다 — 이름이 하나일 때만 읽는다
- 고친 뒤에는 반드시 확인한다: `python -c "import sys;sys.path.insert(0,'scripts');
  import render_report as R;print(R.spec_heights())"` 가 표의 마지막 줄과 같아야 한다

---

**억지로 채우는 글은 넣지 않는다.** 할 말이 없으면 여백이 남는 것이 맞다 —
채움 블록은 **이미 써 둔 분석을 옮겨 붙이는 것**이지, 자리를 메우려고 새로 지어내는 것이 아니다.

## 5. 한도 — 이걸 넘기면 2쪽이 된다

한 장을 지키는 것은 CSS 가 아니라 **글자 수**다.
템플릿은 넘치는 글을 `overflow:hidden` 으로 **감추지 않는다.** 감추면 학부모가 받은 종이에서
문장이 잘린 채 끝나고 아무도 그걸 모른다. 넘치면 2쪽이 되고, 게이트가 막는다.

한도는 **한글로만 채운 최악의 경우**로 쟀다. 영문·숫자가 섞이면 한 줄에 더 들어간다.
「넘치면」 칸의 mm 는 **그 자리가 한 줄 늘 때 지면에서 먹는 높이**다.

| 자리 | 한도 | 넘치면 |
|---|---|---|
| `killer[0].excerpt` | **6줄 · 420자** (줄당 약 70자 · 본문 폭 182mm) | 한 줄에 **4.7mm**. 서술형은 **6줄에서 이미 2쪽**이다 (아래 실측표) |
| `killer[0].choices` | 5개 · 각 40자 | 각 60자면 선지 상자가 14.9 → 25.8mm · **2쪽** |
| `killer[0].conditions` | **3줄 · 각 34자** (서술형) | 조건 상자가 한 줄에 **5.0mm** 커진다. 4줄은 버티고 **5줄이면 2쪽** |
| `killer[0].answer` (서술형) | **한 줄 · 40자** | 칸이 옆으로 길어진다(40자 81mm · 90자 166mm). 종이 폭에 닿는 100자쯤부터 두 줄 |
| `killer[0].title` | 30자 | 머리줄이 두 줄이 되며 대표 문항이 **3.5mm** 커진다 |
| `killer[0].why` | **한 줄 (60자)** | 세 줄로 접히며 **4.4mm**. 칩 칸(52mm)을 뺀 좁은 폭이라 90자면 이미 넘는다 |
| `killer[0].concepts` | **4개** · 각 8자 | **5개부터** 칩이 세 줄로 접히며 6.9mm · 2쪽 |
| `issues[0].reason` | 2줄 (100자) | 이슈 상자가 한 줄에 **4.7mm** |
| `issues[0].excerpt` | 1줄 (60자) | 이슈 상자가 **4.2mm** |
| `difficulty.summary` | 1줄 (45자) | 난이도 상자가 두 줄이 되며 밴드가 **1.3mm** |
| `difficulty.discriminator` | **한 줄 (45자)** | 마무리 상자가 **4.4mm**. 오른쪽 칸이 좁아 90자면 세 줄이다 |
| `overview.highlight` | 1줄 (45자) | 막대 아래 해석이 두 줄이 되며 밴드가 **4.1mm** |
| `summary.quote` | **한 문장** (30자) | 왼쪽 칸이 150px 뿐이다. 40자면 마무리 상자가 **4.7mm** |
| `summary.desc` | 2줄 (90자) | 마무리 상자가 **4.5mm** |
| `next_action` | **한 줄 (30자)** | 45자면 두 줄이 되며 마무리 상자가 **4.1mm** |
| `disclaimer` | **2줄 (약 120자)** | 꼬리말이 고지 한 줄에 **3.8mm**. 한 줄에 약 60자 든다 |
| `meta.scope` | 60자 | 머리글이 두 줄이 되며 **4.5mm** |
| `overview.cards[].value` | 8자 | 카드가 옆으로 벌어져 넷의 폭이 어긋난다(다른 칸이 좁아진다) |

**고지가 발췌와 자리를 다툰다.** `disclaimer` 한 줄(3.8mm)은 발췌 한 줄(4.7mm)에 맞먹는다.
표본의 고지가 78 → 135자로 길어지면서 꼬리말이 9.7 → 13.6mm 가 됐고, 그만큼 발췌 여유가
사라졌다. **고지를 늘렸으면 발췌를 다시 재야 한다.**

### 「6줄」은 **찍힌 줄** 이다 — 원고 줄이 아니다

`report_build.py` 의 `passage_of` 는 **MD 원고의 줄**을 여섯 개 센다. 원고 한 줄이
긴 문단이면 종이에서는 그 한 줄이 대여섯 줄로 접힌다 — 여섯 줄을 지켰는데 2쪽이 나는 길이다.
그래서 한도를 **글자 수로도** 적는다: **약 420자**(6줄 × 70자).
자르는 쪽은 줄 수와 글자 수를 **둘 다** 본다.

### 한도를 넘기면 어떻게 되나 (실측)

발췌를 길게 넣으면 흰 여백을 다 먹고 **넘친다.** 그때 일어나는 일은 이렇다.

- PDF **2쪽.** 둘째 장으로 넘어간 꼬리말이 앞 장 내용과 **겹쳐 찍힌다** —
  글자가 한눈에 사고로 보인다 (PDF 글자를 뽑아 확인했다)
- 쪽 표시도 스스로 **「1 / 2 페이지」**로 바뀐다 — 사고가 종이에 드러난다
- 게이트의 「요약본 1쪽」이 여기서 막는다 (G10 양성 대조가 이 자리를 지킨다)

### 여유분이 얼마나 되나 (실측)

가장 빠듯한 경우는 **서술형 대표 문항 + 이슈 문항 있음**이다 (조건 상자가 선지보다 크다).
발췌를 한 줄씩 늘려 가며 쟀다 — 한 줄이 **4.7mm** 다.
표본 그대로(레이다 있음 · 고지 3줄)이고, 표본의 발췌는 서술형 4줄 · 객관식 5줄이다.

| 발췌 | 서술형 대표 문항 | 여백 | 객관식 대표 문항 | 여백 |
|---|---|---|---|---|
| 4줄 | 81.7mm | 11.1mm · 1쪽 | 77.5mm | 15.4mm · 1쪽 |
| 5줄 | 86.4mm | 6.4mm · 1쪽 | 82.2mm | 10.6mm · 1쪽 |
| **6줄 (빌더 한도)** | 91.2mm | **넘침 1.3mm · 2쪽** | 86.9mm | 5.9mm · **1쪽** |
| 7줄 | 95.9mm | 넘침 6.1mm · 2쪽 | 91.6mm | 넘침 1.9mm · **2쪽** |
| 8줄 | 100.6mm | 넘침 10.9mm · 2쪽 | 96.3mm | 넘침 6.6mm · 2쪽 |

**빌더의 6줄 한도만으로는 한 장이 보장되지 않는다.** 지금 표본대로면 서술형은 **5줄**이
마지막 안전한 값이고, 객관식은 6줄이다. 서술형에서 6줄을 쓰려면 다른 데서 4mm 를
돌려받아야 한다 — 고지를 한 줄 줄이거나(3.8mm), 조건을 두 줄로 줄이거나(5.0mm),
이슈 문항이 없거나(26.7mm) 셋 중 하나다.

그래서 요약본을 만드는 쪽은 **발췌를 6줄까지 자를 수 있다고 믿지 말고**, 서술형이면
5줄로 잡는다. 넘치면 **글을 줄인다** — 조판을 늘리지 않는다.
이 표는 `flex:1 0 auto` (줄어들지 않는 마무리 칸)를 전제로 잰 값이다.
줄어들게 두면 6·7줄이 «1쪽» 으로 나오는데, 그건 겹쳐 찍힌 1쪽이다 (§3 조용한 사고).

### 발췌가 길면

**줄이는 것이지 감추는 것이 아니다.** 셋 중 하나를 고른다.

1. 지문의 **판가름 나는 대목만** 남기고 앞뒤를 `…` 로 줄인다 (가장 좋다)
2. 지문 대신 **발문과 선지만** 싣는다. 지문 전체는 본편 리포트에 있다
3. 그래도 길면 그 문항은 요약본의 대표 문항으로 **부적합**하다. 다른 문항을 고른다

원문을 그대로 실어야 하는 자료는 요약본이 아니라 본편 리포트로 보낸다.

## 6. 흑백 대응

학원 문서는 복사기를 거친다. **색만으로 구분하지 않는다.**

- 난이도 5칸 중 `상` `중상` 은 색이 아니라 **테두리 굵기(1.6pt)** 로 세운다
- 대표 문항 = 1.4pt 실선 테두리, 이슈 문항 = 왼쪽 3pt 굵은 선
- 정답·이슈 갈래 배지는 채우지 않고 **테두리 + 굵은 글씨**
- 막대는 테두리가 있어 0% 도 자리가 보인다 (`mono` 테마에선 빗금으로 바뀐다)
- 본문 최소 7.5pt — 그 아래로 내리지 않는다
- **흑백으로 한 번 출력해 본다.** 이게 가장 확실한 검사다

## 7. 템플릿 계약 (템플릿을 고칠 때만 본다)

지시자는 본편과 같다 (`report-schema.md` 끝 표). 요약본만의 약속 다섯.

**쪽 표시는 한 군데.** 꼬리말 오른쪽 구석이다. 렌더러가 PDF 를 재서 채우므로
한 장이면 `1 / 1 페이지`, 넘치면 `1 / 2 페이지` 가 찍힌다.
「페이지」라는 낱말을 쓰는 이유는 둘이다 — `render_pdf.py` 가 **스스로 찍는 판형으로 보고
도장을 건너뛰고**, 게이트가 그 표기로 쪽수를 대조한다. 「쪽」으로 바꾸면 게이트가 막는다.
그 칸은 `position:absolute` 라 숫자 폭이 바뀌어도 조판이 밀리지 않는다(쪽수 1패스 수렴).

**`section-title` 클래스를 단 요소 한 개.** 렌더러는 「쪽번호 앞에 섹션 제목이 있어야 한다」를
강제하고, 그 글자를 PDF 에서 찾아 몇 쪽인지 읽는다. 요약본에는 섹션 제목이 없으므로
머리글의 「기출 분석 요약」 배지가 그 역할을 겸한다. **이 class 이름을 바꾸면 렌더가 실패한다.**

**바깥 상자는 `page` 와 `sheet` 두 클래스를 함께 단다.** 게이트가 장 수를 `.page` 로 세고,
조판 규칙(고정 높이·세로 배분)은 `.sheet` 가 갖는다.

**`<!-- INTERNAL -->`** 은 꼬리말의 «발송 전 확인» 네 줄에 쓴다. 배포본에는 찍히지 않는다.

**강조는 class 가 아니라 «속성»으로 켠다.** 강조 카드(`data-unit` 이 빈 칸 · `data-key`)와
강조 막대(`data-em`)가 그렇다. 게이트가 카드와 막대를 **class 이름 글자 그대로** 세기
때문에, class 뒤에 낱말을 덧붙이면 「막대가 0줄」·「카드 수가 안 맞는다」로 멀쩡한 리포트가
막힌다 — 실제로 막혔다. 레이다도 같은 이유로 `data-ok` 를 쓴다(비면 상자째 사라진다).
**이 속성 이름들을 class 로 되돌리지 않는다.**

### 7-1. 주석에 적으면 안 되는 것 (두 번 데였다)

게이트는 HTML 을 **글자로** 센다. 주석도 글자다. 그래서 템플릿 주석에

- **쪽 표시 꼴**(숫자 빗금 숫자 «페이지»)을 예로 적으면 → 「총쪽수를 두 가지로 말한다」로 막힌다
- **세는 class 이름을 따옴표째** 적으면 → 「정답이 두 개」처럼 개수 검사가 어긋난다

설명은 낱말로 풀어 쓴다. 지금 템플릿 주석이 그렇게 돼 있다.

### 7-2. 빈 목록이 사라지게 하는 법

선지 상자와 조건 상자는 **여는 태그 바로 뒤에 REPEAT 를 붙여 한 줄로** 쓴다.
줄바꿈이 한 칸이라도 남으면 목록이 비어도 그 칸이 «빈 문자열이 아닌» 것이 되어
`:empty` 가 듣지 않고 **빈 테두리가 인쇄된다.**

### 7-3. 마무리 상자 안에 가로 구분선을 긋지 않는다

「다음 행동」 줄을 가로선으로 나눴더니 상자 안에 긴 가로줄이 셋이 되어,
게이트의 **«표 머리글» 검사가 마무리 상자를 표로 잘못 읽고 막았다.**
지금은 이름표를 테두리 칩으로 세워 구분을 대신한다.

## 8. 검증

발행 전에 **반드시 돌린다.**

```bash
python scripts/render_report.py report.json out/ --summary   # 콘솔에 PDF 실측 쪽수가 찍힌다
python scripts/gate_check.py out/ report.json                # 2쪽이면 여기서 막힌다
```

손으로도 본다.

- [ ] **PDF 가 1쪽인가** ★ (게이트가 막지만, 막힌 뒤에 고치면 늦다)
- [ ] **마무리 상자가 꼬리말을 덮지 않았는가** — 겹침은 쪽수로 안 잡힌다. 눈으로 본다
- [ ] 흑백으로 한 번 출력 — 난이도 `상` 칸과 이슈 배지가 구분되는가
- [ ] 대표 문항의 정답이 원본과 같은가
- [ ] **서술형 대표 문항이면** — 「본문참조」가 아니라 **모범답안 한 줄**이 찍혔는가,
      〈조건〉 상자가 읽히는가 (PDF 글자로 확인: «본문참조» 없음 · «모범답안» 있음)
- [ ] 이슈 문항이 **사실인가** — 추측을 「복수정답」이라고 적지 않는다
- [ ] 숫자마다 근거가 붙어 있는가 (`disclaimer` 에 추정치 고지)
- [ ] 학생 이름·개인정보가 없는가 — 요약본은 여러 집에 같은 장이 나간다
- [ ] 불안을 자극하는 문장이 없는가 (`korean-writing`)
- [ ] 발췌가 한도 안인가 — **서술형이면 5줄**, 객관식이면 6줄 (§5)
- [ ] 고지(`disclaimer`)가 두 줄을 넘지 않았는가 — 한 줄이 발췌 한 줄만큼 자리를 먹는다
- [ ] **레이다가 섰는가** — 유형이 셋 미만이면 상자가 통째로 사라진다. 사라진 것이
      맞는지 한 번 본다 (§2-1)

### 채움 블록을 켜는 쪽에 (렌더러 담당)

§4-1 실측표가 그 판단의 정본이다. 빌더는 `fill_blocks` 에 «무엇을 어떤 차례로» 만 담고

빌더가 `sections_summary` 로 직접 받으려면 아래를 더해야 한다.

| `fill-home` | `parent_note` |

### 아직 열려 있는 것 (게이트 담당)

**닫힌 것** — `gate_check.py` 의 「대표 문항 속살」이 «선지 ≥ 2 **또는** 조건 ≥ 1» 로 바뀌어
서술형 대표 문항을 더는 막지 않는다. 조건 줄의 class 이름은 `cond` 다.

**열린 것 둘.**

- **발췌 한도가 서술형에서 헐겁다.** 게이트의 `EXCERPT_LINES` 가 6인데, 지금 판형에서
  서술형 대표 문항 + 이슈 + 고지 3줄이면 **6줄이 이미 2쪽**이다 (§5 실측표).
  게이트는 「요약본 1쪽」에서 결국 막지만, 막히는 자리가 발췌 검사가 아니라 쪽수 검사다 —
  사람에게는 «왜 2쪽인지» 가 안 보인다. 한도를 갈래별로 가르는 편이 낫다
- **강조 카드 검사가 지금 판형을 못 본다.** `CARD_KEY` 는 `class="card … key"` 를 찾는데
  판형은 강조를 **속성**(`data-unit` 이 빈 칸)으로 가른다 — class 에 낱말을 붙이면 카드
  개수 검사가 어긋나기 때문이다 (§2-1). 그래서 이 검사는 늘 0 을 세고 아무것도 못 잡는다.
  속성 쪽을 보게 고쳐야 한다

### 이름 — 꼬리칸은 «요약본»

파일 이름의 **«요약본»** 이 게이트가 요약본을 알아보는 표다 (`gates.md` §5).
공용 어휘(`gonggam-material-studio/assets/filename_check.py` 의 `TAIL`)에 그 낱말이 들어갔고
렌더러도 그 꼬리칸을 쓴다 — 이름과 실물이 이어져 있다.
발췌가 12줄인 2쪽 산출물을 게이트에 넣으면 「요약본 1쪽」과 「쪽번호 장마다 일치」가
**둘 다 막는 것**을 확인했다.
